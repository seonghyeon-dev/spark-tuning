## 2. 원인 및 조치

### 2.1 처리 회차 분할 — 소요시간 30% 감소

- Compaction 처리 단위: 파티션별로 파일을 묶은 file group
- 동시 처리 group 수: `max-concurrent-file-group-rewrites`로 결정

**원인** — group 7개를 2개씩 처리, 4회차로 분할. 회차별로 느린 쪽 종료까지 대기

| 회차 | 처리 대상 | 데이터 비중 | 소요시간 비중 |
|------|----------|-----------|-------------|
| 1 | 1.4GB + 2.8GB | 11% | 21% |
| 2 | 9.7GB + 2.2GB | 32% | 27% |
| 3 | 9.9GB + 10.2GB | 54% | 29% |
| 4 | 1.5GB (단독) | 4% | 17% |

- 1·4회차: 데이터 15%에 소요시간 37% 사용
- CPU 64 core 중 58% 유휴

**조치**

| 설정 | 변경 | 효과 |
|------|------|------|
| `max-concurrent-file-group-rewrites` | 2 → 10 → **12** | 1회차로 처리 (12는 재처리 3시간치 = group 12개 기준, 2026-09-21) |
| `max-file-group-size-bytes` | 10GB → 기본값 | group 7개 → 4개 (파티션당 1개) |

### 2.2 리소스 과다 — 리소스 비용 13% 감소

**원인** — 2.1 조치 후 유휴 CPU 25~29% 잔존

**조치** — executor 16 → 12. 축소 한계 확인을 위해 3개 지점 측정

| executor | 소요시간 (초/GB) | 리소스 비용 (dcu/GB) | 유휴 CPU | disk spill |
|----------|----------------|-------------------|---------|-----------|
| 16 | 2.03 | 0.00251 | 25~29% | 0 |
| **12** | 2.41 | **0.00219** | 17% | 0 |
| 8 | 3.77 | 0.00247 | 15% | 0 |

- 8: CPU 33% 감소 대비 소요시간 56% 증가 → 리소스 비용 반등
- 하한: 12

### 2.3 무효 설정 — 삭제

| 설정 | 확인 방법 | 결과 |
|------|----------|------|
| `advisory-partition-size` 768MB | 삭제 전후 비교 | 파일당 크기 507.9 → 507.0MB |
| `coalescePartitions.parallelismFirst` false | true로 전환 | 파일당 크기 509 → 510MB |

- 출력 파일 크기 결정 요소: `target-file-size-bytes`(512MB) 단독
- Iceberg가 shuffle partition 수를 직접 산정 → 두 Spark 설정 미개입

## 5. executor 자동 조절 — Dynamic Allocation 채택

데이터가 늘면 소요시간이 늘어 실행 창(12분)을 넘고, 그때마다 사람이 대수를 고쳐야 한다. Spark의 Dynamic Allocation으로 자동화한다.

**그냥 켜면 안 되는 이유** — Spark은 기본적으로 밀린 일감을 전부 동시에 처리할 만큼 부른다. 우리 작업은 일감이 잘게 쪼개져 있어 **185대까지 요청한다.**

**해법: `executorAllocationRatio`** — "전부 동시에 처리할 대수의 몇 %만 부를지"를 정하는 Spark 설정이다. **13%**로 설정했다.

```
데이터 39GB → 밀린 일감 351개 → 전부 동시에 하려면  88대 → 13% = 12대
데이터 82GB → 밀린 일감 738개 → 전부 동시에 하려면 185대 → 13% = 24대
```

**비율은 고정인데 대수는 데이터에 따라 자동으로 변한다.**

**검증 결과** (7회)

| 확인 항목 | 결과 |
|----------|------|
| 1시간 데이터에서 기존과 동등한가 | 소요시간 +3.7%, 자원 +5.9% (오차 범위 이내) |
| 데이터가 늘면 대수가 늘어나는가 | 39GB 12대 → **82GB 24대** |
| 상한이 아니라 비율이 대수를 정하는가 | 상한 36대로 풀어도 **24대에서 멈춤** |
| disk spill | 7회 전부 0 |

정적 12대로 82GB를 처리하면 약 205초가 걸린다. 자동 조절로 **111초**로 줄었고 GB당 자원 사용량은 동일하다.

**설정**

| 설정 | 값 | 테이블별 |
|------|-----|---------|
| `executorAllocationRatio` | 0.13 | 공통 |
| `executor.instances` / `initialExecutors` / `minExecutors` | **세 값 동일.** 시간당 데이터GB × 0.32 — 1번 12, 2번 8, 3번 12, 4번 12 | **테이블별** |
| `maxExecutors` | 36 | 공통 |
| executor memory | 1번 16g, 2번 20g, 3·4번 18g | **테이블별** |
| executor `memoryOverhead` | **3g** (4g → 3g. 1g는 job 실패, 2g는 executor 유실) | 공통 |

비율(%)은 데이터 크기와 무관하므로 공통이고, 개수(대)는 테이블 크기에 비례하므로 테이블별이다.

**`memoryOverhead`란** — executor pod 메모리 한도 = executor memory(heap) + `memoryOverhead`. heap은 Spark가 데이터 row를 올려놓고 정렬하는 공간이고 부족하면 디스크로 내려보낸다(spill — 느려지지만 안 죽음). overhead는 프로그램이 데이터 말고 돌아가는 데 쓰는 메모리다 — ①executor끼리 shuffle 조각을 주고받는 통신 버퍼(가장 큼) ②Java 프로그램 자체(코드·스레드·GC 장부) ③압축·해제 작업 공간 — 부족하면 K8s가 executor를 죽인다. 필요량은 동시 task 수(4)로 정해져 데이터 양·heap 크기와 무관하므로 3g 고정이다. 기본값 10%(1.8g)는 ②만 보고 잡은 값이라 부족했다(2g에서 executor 유실, heap 18g·20g 모두). 상세는 설계서 §8.4

**⚠️ `executor.instances`를 반드시 같은 값으로.** 이 값이 남아 있으면 Dynamic Allocation의 시작 대수가 여기에 묶여 비율 설정이 무력화된다. 2번 테이블 테스트에서 비율과 시작 대수를 어떻게 바꿔도 12대로 돈 원인이었다.

**1번 테이블 재검증 (2회, 2026-09-21)** — 16g + `memoryOverhead` 3g로 1시간치 13대·9시간치 36대 spill 0·task error 0. 16g 확정.

**2번 테이블 검증 (12회, 2026-09-15~21)** — 시간당 24GB, row 수는 1번과 같음(수직분할)

| 확인 항목 | 결과 |
|----------|------|
| 대수 산정 | 24GB × 0.32 = 8대. 비율 0.13이 실제로 8대로 수렴 — **1번에서 잡은 계수가 그대로 맞음** |
| 12대 vs 8대 | 소요시간 1.5 → 1.9분이지만 자원 비용 **−10~16%**. 1번의 16 → 12대 축소와 같은 결과. 확정 설정(시작 대수 8)으로는 **1.7분** |
| disk spill | 16g에서 시간대별로 1.6~10.4GiB 발생 → **20g에서 0.** row가 좁아 파일 하나에 row가 60% 더 들어가고, task당 정렬 메모리(16g 기준 2.4GB)를 넘어섬 |
| 18g 재검증 | 1시간치 18g spill 0이었으나 **20시간치에서 spill 936MiB** → 규칙(spill 0인 최소값)상 **20g 유지** |
| 테이블 간 비교 | GB당 비용은 1번보다 높게 보이나 row 수가 같으므로 **row당 비용으로 비교** — 1번 12대와 같은 수준 |

**3번 테이블 검증 (9회, 2026-09-16~21)** — 시간당 37~40GB, 1번과 같은 급

| 확인 항목 | 결과 |
|----------|------|
| 대수 산정 | 39GB × 0.32 = 12대. 8대로 시작해도 비율 0.13이 12대로 올림 — 2번(8대)과 함께 **공통 비율 확정** |
| disk spill | 16g에서 2회 모두 발생 → 20g에서 4회 0 → **18g에서 3회 0(1·2·22시간치). 18g 확정** |
| 비용 | row당 비용이 1번보다 30% 높으나 4회 일관 — 컬럼 구성 차이(메모리 팽창)로 설정과 무관 |
| 메모리 비용 | 16g → 20g로 자원 비용 +5~6%. **메모리는 spill을 없애는 최소값만** 올린다 |

**4번 테이블 검증 (14회, 2026-09-17~21)** — 3번과 같은 급, 같은 결과. 12대 + **18g** + `memoryOverhead` 3g 확정. 1~6시간치 전부 spill 0·task error 0. **4개 테이블 검증 완료.**

**idle cores 17~25%에 대해** — 12대(48 slot)에 쓰기 task가 74~77개라 둘째 회차에 slot이 남아서 생기는 구조적 값이다. 1번 확정값 16.7%와 같은 원인이며 판정 기준(spill 0 + 자원 비용 최저)과 무관하다

**여러 시간치 재처리도 같은 설정으로 된다** — 1번 9시간치 36대 4.0분, 2번 20시간치 23대 10.9분, 3번 22시간치 36대 10.4분, 4번 6시간치 33대 3.1분, 전부 task error 0. 12대·18g는 파티션 1개(시간 × `par_a`, 약 17GB)에 맞춘 값이고 데이터가 늘면 파티션 개수만 늘어 시간만 는다. 1시간치당 비용은 오히려 25% 내려간다(고정 비용이 묻힘). 천장 36대에서 duration ≈ 시간 수 × 0.5분

**executor 수는 동시에 도는 파티션 수가 정한다** — Compaction은 파티션을 `max-concurrent-file-group-rewrites`개씩 동시에 돌리고 자동 증원은 지금 도는 파티션의 일감만 본다. 그래서 2번(파티션 10GB)은 23대, 3·4번(17GB)은 31~36대에서 수렴하며 데이터를 더 넣어도 안 는다. 이 설정을 10 → 12로 올렸다(재처리 3시간치 = 파티션 12개를 한 번에). 상한 16 — 큰 파티션 7개면 천장 36대가 꽉 차 그 위는 디스크만 는다

**executor 디스크(`spark-local-dir-1`)** — hourly executor당 shuffle 약 5GiB(60GiB ÷ 12대), 권장 10GiB × 노드당 executor 수. 22시간치가 현 디스크로 성공했으므로 용량은 충분하며 운영 첫 실행에서 사용량 1회 확인

**참고** — Dynamic Allocation은 보통 "일이 없으면 반납"이 핵심 기능이나, 우리 작업은 일감이 계속 밀려 있어 반납이 발생하지 않는다. **부르는 양을 조절하는 쪽만 사용한다.** 공식 문서에 명시된 용도이며, 반납을 하지 않으므로 Dynamic Allocation 사용 시 흔히 지적되는 데이터 손실 위험도 해당하지 않는다.

**유일한 주의점** — 비율값 13%는 현재 입력 파일 크기(약 54MB)를 전제로 계산했다. append 설정이 바뀌어 파일 크기가 달라지면 **에러 없이 대수만 어긋난다.** 재계산이 필요하다.

## 6. 남은 작업

| 항목 | 내용 |
