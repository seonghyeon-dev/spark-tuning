# hourly Compaction 튜닝 결과

| 항목 | 내용 |
|------|------|
| 대상 | hourly Compaction Job (테이블 4개) |
| 기간 | 2026-08-11 ~ 08-12, 9회 측정 |
| 결과 | 소요시간 26% 감소, 리소스 비용 47% 감소 |

---

## 결과

| 지표 | 변경 전 | 변경 후 |
|------|--------|--------|
| 소요시간 (초/GB) | 3.24 | 2.41 (−26%) |
| 리소스 비용 (dcu/GB) | 0.00416 | 0.00219 (−47%) |
| 유휴 CPU | 58% | 17% |
| DAG 전체 (테이블 4개) | 10~12분 | 약 6분 |
| executor | 16개 | 12개 |

hourly Compaction은 매시 45분에 시작해 정각까지 끝나야 한다. 기존에는 12분 창에서 10~12분을 써서 여유가 3분뿐이었으나, 약 6분으로 줄어 여유가 6분으로 늘었다.

리소스는 executor를 16개에서 12개로 줄여 CPU 16 core, 메모리 64GB를 절감했다. 같은 클러스터에서 5분 주기로 도는 append Job과의 경합이 줄어든다.

---

## 확정 설정

| 설정 | 변경 전 | 변경 후 |
|------|--------|--------|
| `max-concurrent-file-group-rewrites` | 2 | **10** |
| `max-file-group-size-bytes` | 10GB | **기본값 100GB (설정 제거)** |
| `num-executors` | 16 | **12** |
| `driver cpu` | 1 | **2** |
| `advisory-partition-size` | 768MB | **삭제** |
| `coalescePartitions.parallelismFirst` | false | **삭제 가능** |

아래는 검토 후 변경하지 않았다.

| 설정 | 값 | 이유 |
|------|-----|------|
| `target-file-size-bytes` | 512MB | 스키마 설계에서 확정된 값 |
| `rewrite-all` | true | 입력 파일이 전부 합칠 대상이므로 false로 바꿔도 처리량이 같다 |
| `executor cpu / memory` | 4 core / 16GB | 메모리를 89~94% 쓰면서 disk spill이 0이다. 줄이면 spill이 시작된다 |
| `partial-progress.enabled` | 기본값 (false) | 바꾸면 snapshot이 늘어 보존 정책과 재처리 DAG에 영향을 준다 |
| rewrite 전략 | `sort` | 미적용 시 조회가 40% 느려진다 (읽기 성능 테스트 §5.4) |

---

## 개선의 대부분은 한 가지 설정에서 나왔다

`max-concurrent-file-group-rewrites`가 소요시간의 30%를 줄였다. 나머지 설정은 리소스 절감이거나 효과가 없었다.

Compaction은 파티션별로 파일을 묶어 "file group" 단위로 처리한다. 이 값이 **동시에 처리할 group 수**를 정한다.

기존에는 group이 7개인데 2개씩만 처리해서 4회차로 나뉘었다.

| 회차 | 처리 대상 | 데이터 비중 | 소요시간 비중 |
|------|----------|-----------|-------------|
| 1회차 | 작은 파티션 2개 (1.4GB + 2.8GB) | 11% | 21% |
| 2회차 | 큰 파티션 (9.7GB + 2.2GB) | 32% | 27% |
| 3회차 | 큰 파티션 (9.9GB + 10.2GB) | 54% | 29% |
| 4회차 | 자투리 1개 (1.5GB, 짝이 없어 단독 실행) | 4% | 17% |

1회차와 4회차가 **데이터 15%를 처리하며 시간의 37%를 썼다.** CPU 64 core를 확보했지만 동시에 2 group만 도니 절반 이상이 놀고 있었다 (유휴 58%).

동시 처리를 10으로 올려 1회차로 처리하게 바꿨다. `max-file-group-size-bytes`를 기본값으로 되돌려 group도 7개에서 4개(파티션당 1개)로 줄였다.

---

## 모니터링 도구의 진단을 그대로 따르면 안 된다

DataFlint가 "유휴 CPU 58%, 클러스터가 과다 프로비저닝됨"이라는 경고와 함께 **executor를 줄이라고** 제안했다.

그러나 원인은 리소스 과다가 아니라 병렬성 제약이었다. 제안대로 executor를 줄였다면 유휴 CPU는 사라지지만 **소요시간은 그대로 120초**였을 것이다.

유휴 CPU가 높은 원인은 두 가지이고 처방이 반대다.

| 원인 | 처방 |
|------|------|
| 리소스 과다 | executor 축소 |
| 병렬성 제약 | 제약 해제 |

DataFlint는 Spark 지표만 보고 Iceberg 옵션을 알지 못하므로 전자만 제안한다. 병목의 원인은 Spark UI의 job 목록에서 file group 처리 순서를 직접 확인해야 드러났다.

---

## executor는 12개가 하한이다

executor를 줄이면 소요시간은 늘고 리소스 비용은 준다. 어디까지 줄일 수 있는지 3개 지점을 측정했다.

| executor | 소요시간 (초/GB) | 리소스 비용 (dcu/GB) | 유휴 CPU |
|----------|----------------|-------------------|---------|
| 16 | 2.03 | 0.00251 | 25~29% |
| **12** | 2.41 | **0.00219** | 17% |
| 8 | 3.77 | 0.00247 | 15% |

**8개에서 리소스 비용이 다시 올라간다.** CPU를 33% 줄였는데 소요시간이 56% 늘어 순손실이다. 이미 CPU가 병목이라 유휴가 17%에서 15%로 거의 줄지 않은 것이 근거다.

12개에서 disk spill이 0을 유지하는 것도 확인했다.

## 출력 파일 품질

Compaction의 목적은 작은 파일을 합치는 것이므로 결과 파일 크기가 실제 성과다.

| 항목 | Compaction 전 | Compaction 후 |
|------|--------------|--------------|
| 파일 수 | 703개 | 75개 |
| 평균 크기 | 53.9MB | 509MB |
| 최대 크기 | 72.3MB | 607MB |

목표 크기가 512MB이므로 평균 509MB는 사실상 최적이다. 이 부분은 튜닝 전에도 정상이었고, 이번 튜닝으로 나빠지지 않았음을 9회 전부 확인했다.

**최소 크기는 300~415MB로 흔들리며, 이는 조치하지 않는다.** 원인은 `col_a=D` 파티션이 시간당 600~830MB로 작다는 것이다. Iceberg는 512MB 기준으로 파일을 나누므로 623MB는 311MB 파일 2개가 된다. 전체 파일 75개 중 2개, 데이터 37GB 중 0.9GB(2.4%)에 해당한다.

해소하려면 목표 파일 크기를 830MB 이상으로 올려야 하는데 그러면 모든 파티션의 파일이 커져 스키마 설계 결정을 뒤집는다. 2.4% 데이터를 위해 치를 비용이 아니다.

## 남은 작업

| 항목 | 내용 |
|------|------|
| executor 상한 확정 | 데이터 증가 시 executor를 자동 산정하려면 K8S 리소스 할당량 확인이 필요하다 |
| 나머지 테이블 3개 검증 | 파티션 값 개수가 다르면 file group 수가 달라진다 |
| **daily Compaction 점검** | hourly가 정리한 뒤라 할 일이 없어야 하는데 888GB에 30~60분이 걸린다. 전체를 다시 쓰고 있는지 확인이 필요하다 |

daily 쪽이 개선 여지가 가장 클 것으로 본다. hourly가 매시간 정리해 두므로 daily는 합칠 파일이 거의 없어야 하는데, 소요시간이 데이터 양에 비례하고 있다.
