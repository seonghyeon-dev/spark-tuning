# 구현 검증

## 목적

프로젝트에 등록된 검증 **에이전트**와 `verify-*` **스킬**을 실행하여 통합 검증을 수행합니다:

- 각 스킬의 Workflow에 정의된 검사를 실행
- 각 스킬의 Exceptions를 참조하여 false positive 방지
- 발견된 이슈에 대해 수정 방법을 제시
- 사용자 승인 후 수정 적용 및 재검증

## 실행 시점

- 새로운 기능을 구현한 후
- Pull Request를 생성하기 전
- 코드 리뷰 중
- 코드베이스 규칙 준수 여부를 감사할 때

## 실행 대상

### 검증 에이전트 (병렬 실행)

각 에이전트는 **자기 컨텍스트에서 읽기 전용으로** 검사하고 결과 보고서만 반환합니다. 서로 독립적이므로 **한 번에 전부 dispatch** 합니다.

| # | 에이전트 | 설명 | 검사 대상 |
|---|----------|------|-----------|
| 1 | `verify-column-naming` | TABLE_A 컬럼 명명 규칙 위반 및 폐기된 옛 표기 잔존 | `CLAUDE.md`, `tuning/*.md`, `schema/*.md`, `pipeline/**/*.md`, `pipeline/**/*.py` |
| 2 | `verify-doc-consistency` | 확정값(설정값·cron·버전·실측 수치)의 `CLAUDE.md` ↔ 가이드 ↔ 보고용 요약 3자 대조, 목표/운영 버전 구분, 미확인 마커 동기화 | `CLAUDE.md`, `tuning/*.md`, `schema/*.md`, `pipeline/*.md`, `pipeline/**/*.py` |

### 검증 스킬 (순차 실행)

에이전트로 분리하기 어려운 검사(대화 맥락 의존, 사용자 확인 필요)는 스킬로 둡니다.

(아직 등록된 검증 스킬이 없습니다)

> **에이전트와 스킬 중 무엇으로 만들 것인가**: 읽기 전용 스캔이고 결과만 받으면 되는 검사는 **에이전트**(컨텍스트 절약 + 병렬). 수정 적용까지 하거나 사용자와 대화가 필요한 검사는 **스킬**. 등록은 `/manage-skills`가 관리합니다.

## 워크플로우

### Step 1: 소개

위의 **실행 대상** 섹션에 나열된 에이전트와 스킬을 확인합니다.

선택적 인수가 제공된 경우, 이름이 일치하는 항목만 필터링합니다.

**에이전트·스킬이 모두 0개인 경우:**

```markdown
## 구현 검증

등록된 검증 항목이 없습니다. `/manage-skills`를 실행하여 프로젝트에 맞는 검증을 생성하세요.
```

이 경우 워크플로우를 종료합니다.

**1개 이상인 경우:**

실행 대상 테이블의 내용을 표시합니다:

```markdown
## 구현 검증

검증 에이전트 N개를 병렬 실행하고, 검증 스킬 M개를 순차 실행합니다.

| # | 항목 | 종류 | 설명 |
|---|------|------|------|
| 1 | verify-<name1> | 에이전트 | <description1> |
| 2 | verify-<name2> | 스킬 | <description2> |

검증 시작...
```

### Step 2: 실행

#### 2A. 검증 에이전트 병렬 dispatch

**실행 대상 → 검증 에이전트** 표의 모든 에이전트를 **한 메시지에서 동시에** 호출합니다. 하나씩 호출하면 병렬화 이점이 사라집니다.

각 호출에 다음을 전달합니다:

- 검사 범위 (기본: 에이전트 정의의 검사 대상 전체 / 인수로 특정 파일이 지정되면 그 목록)
- 이번 세션에서 확립됐지만 에이전트가 모를 수 있는 판정 기준

> **⚠️ 에이전트는 이 대화의 맥락을 상속하지 않습니다.** `CLAUDE.md`는 읽지만, 이 세션에서 새로 정한 규칙·미확정 사항은 모릅니다. 그런 것이 있으면 **호출 프롬프트에 직접 실어야** 합니다. 안 실으면 에이전트는 옛 기준으로 판정하고, 그 사실이 보고서에 드러나지 않습니다.

**에이전트 결과를 검증 없이 그대로 신뢰하지 않습니다.** 다음은 반드시 원본을 확인합니다:

| 신호 | 확인 방법 |
|------|-----------|
| `예외 처리: 0건` | 검사가 실제로 동작했는지 의심. 탐지 패턴을 직접 한 번 실행 |
| 위반이 비정상적으로 많음 | 예외 규칙 오적용 가능성. 첫 3건의 원문을 직접 읽기 |
| 보고에 없던 수치가 등장 | 추정치일 수 있음. 출처 파일에서 Grep으로 대조 |

#### 2B. 검증 스킬 순차 실행

**실행 대상 → 검증 스킬** 표의 각 스킬에 대해 순서대로 수행합니다.

##### 2B-a. 스킬 SKILL.md 읽기

해당 스킬의 `.claude/skills/verify-<name>/SKILL.md`를 읽고 다음 섹션을 파싱합니다:

- **Workflow** — 실행할 검사 단계와 탐지 명령어
- **Exceptions** — 위반이 아닌 것으로 간주되는 패턴
- **Related Files** — 검사 대상 파일 목록

##### 2B-b. 검사 실행

Workflow 섹션에 정의된 각 검사를 순서대로 실행합니다:

1. 검사에 명시된 도구(Grep, Glob, Read, Bash)를 사용하여 패턴 탐지
2. 탐지된 결과를 해당 스킬의 PASS/FAIL 기준에 대조
3. Exceptions 섹션에 해당하는 패턴은 면제 처리
4. FAIL인 경우 이슈를 기록:
   - 파일 경로 및 라인 번호
   - 문제 설명
   - 수정 권장 사항 (코드 예시 포함)

##### 2B-c. 항목별 결과 기록

각 항목 완료 후 진행 상황을 표시합니다:

```markdown
### verify-<name> 검증 완료

- 검사 항목: N개
- 통과: X개
- 이슈: Y개
- 면제: Z개

[다음 항목으로 이동...]
```

### Step 3: 통합 보고서

모든 스킬 실행 완료 후, 결과를 하나의 보고서로 통합합니다:

```markdown
## 구현 검증 보고서

### 요약

| 검증 스킬 | 상태 | 이슈 수 | 상세 |
|-----------|------|---------|------|
| verify-<name1> | PASS / X개 이슈 | N | 상세... |
| verify-<name2> | PASS / X개 이슈 | N | 상세... |

**발견된 총 이슈: X개**
```

**모든 검증 통과 시:**

```markdown
모든 검증을 통과했습니다!

구현이 프로젝트의 모든 규칙을 준수합니다:

- verify-<name1>: <통과 내용 요약>
- verify-<name2>: <통과 내용 요약>

코드 리뷰 준비가 완료되었습니다.
```

**이슈 발견 시:**

각 이슈를 파일 경로, 문제 설명, 수정 권장 사항과 함께 나열합니다:

```markdown
### 발견된 이슈

| # | 스킬 | 파일 | 문제 | 수정 방법 |
|---|------|------|------|-----------|
| 1 | verify-<name1> | `schema/trino-query-guide.md:51` | 문제 설명 | 수정안 |
| 2 | verify-<name2> | `CLAUDE.md:75` | 문제 설명 | 수정안 |
```

### Step 4: 사용자 액션 확인

이슈가 발견된 경우 `AskUserQuestion`을 사용하여 사용자에게 확인합니다:

```markdown
---

### 수정 옵션

**X개 이슈가 발견되었습니다. 어떻게 진행할까요?**

1. **전체 수정** - 모든 권장 수정사항을 자동으로 적용
2. **개별 수정** - 각 수정사항을 하나씩 검토 후 적용
3. **건너뛰기** - 변경 없이 종료
```

### Step 5: 수정 적용

사용자 선택에 따라 수정을 적용합니다.

> **⚠️ 수정은 반드시 이 세션에서 직렬로 적용합니다.** 검증 에이전트는 읽기 전용이며 수정 권한이 없습니다. 여러 에이전트에게 같은 문서를 동시에 고치게 하면 충돌합니다. **읽기는 병렬, 쓰기는 직렬**이 원칙입니다.

**"전체 수정" 선택 시:**

모든 수정을 순서대로 적용하며 진행 상황을 표시합니다:

```markdown
## 수정 적용 중...

- [1/X] verify-<name1>: `schema/trino-query-guide.md` 수정 완료
- [2/X] verify-<name2>: `CLAUDE.md` 수정 완료

X개 수정 완료.
```

**"개별 수정" 선택 시:**

각 이슈마다 수정 내용을 보여주고 `AskUserQuestion`으로 승인 여부를 확인합니다.

### Step 6: 수정 후 재검증

수정이 적용된 경우, 이슈가 있었던 스킬만 다시 실행하여 Before/After를 비교합니다:

```markdown
## 수정 후 재검증

이슈가 있었던 스킬을 다시 실행합니다...

| 검증 스킬 | 수정 전 | 수정 후 |
|-----------|---------|---------|
| verify-<name1> | X개 이슈 | PASS |
| verify-<name2> | Y개 이슈 | PASS |

모든 검증을 통과했습니다!
```

**여전히 이슈가 남은 경우:**

```markdown
### 잔여 이슈

| # | 스킬 | 파일 | 문제 |
|---|------|------|------|
| 1 | verify-<name> | `schema/read-performance-test.md:259` | 자동 수정 불가 — 수동 확인 필요 |

수동으로 해결한 후 `/verify-implementation`을 다시 실행하세요.
```

## 예외사항

다음은 **문제가 아닙니다**:

1. **등록된 스킬이 없는 프로젝트** — 오류가 아닌 안내 메시지를 표시하고 종료
2. **스킬의 자체적 예외** — 각 verify 스킬의 Exceptions 섹션에 정의된 패턴은 이슈로 보고하지 않음
3. **verify-implementation 자체** — 실행 대상 스킬 목록에 자기 자신을 포함하지 않음
4. **manage-skills** — `verify-`로 시작하지 않으므로 실행 대상에 포함되지 않음
5. **에이전트가 `판정불가`로 보고한 항목** — 이슈가 아니라 **호출자가 확인할 목록**이다. 자동 수정 대상에 넣지 않고 보고서에 별도로 나열한다
